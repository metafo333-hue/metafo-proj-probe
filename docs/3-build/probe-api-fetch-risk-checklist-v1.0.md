> 🔴 诚实标注：`现状` 列区分「🔴已是代码缺口」「⚠️接入时会踩」「📋合规红线已声明」「✅已防」——不假装已防。

## 〇、闭环定位

```
本文档（问题库 · 看见有哪些坑）
   │  每条坑 → 指派一个对策归属
   ├─→ 成本类  → 成本埋点设计（让烧钱可见 + 双本账对账）
   ├─→ 应对类  → 数据动态智能管控（每次调取动态决定 调/缓/降/拦）
   └─→ 质量类  → audit 8 闸（污染/同源/伪权威）
机制：清单发现问题 → 归口对策文档设计 → S1 落码 → 回填「现状」列 → 新坑再入库
```

## 一、用法（怎么过 gate）

### 1.1 接入新数据源时（S1 逐条过）
按 §三 九大类逐条核对，每条回答「本源是否会踩 → 对策是否就位」。**全部 ✅/N.A. 才允许把 ledger status 置 active**。

### 1.2 上线后遇新坑时（持续补充）
1. 按 §四「新坑入库规范」给坑**编号**（沿用 C/D/L/E/M/U/F/W/Q/K 前缀）
2. 填 触发 / 后果 / 对策 / 现状 / 关联对策文档
3. 在 §五 变更记录追一行 + 升 patch 版本
4. 若该坑催生新对策 → 同步到埋点/管控设计文档

### 1.3 编号体系
| 前缀 | 类别 | 主对策归口 |
|------|------|-----------|
| **C** | 成本（数据源面）| 埋点 + 动态管控 |
| **M** | 成本（LLM 面）| 埋点 + 动态管控 |
| **F** | 扇出/并发放大 | 动态管控 |
| **W** | 持续监测/订阅 | 动态管控 |
| **D** | 数据真实性/污染 | audit 8 闸 |
| **L** | 合规红线 | registry gate19 + P0 |
| **U** | 输入/链接解析 | 动态管控（前置） |
| **E** | 工程/可用性 | 各模块 |
| **Q** | 多租户/可观测 | 埋点 + 动态管控 |
| **K** | 缓存次生坑（加缓存后引入）| 动态管控 |

## 二、最该先堵（按 ROI · 截至 v1.0）

1. **Q3 成本看板缺失** —— 让 C/M/F/W 全部「烧完才知道」的元缺口。先做埋点（per-source/per-LLM 计量）= 一切的数据基础。
2. **C1+C2+M5 无结果缓存** —— 直接对应「重复调用涨成本」，命中即省。
3. **C3+C4+M1 重试/fallback 雪崩 + 失败仍扣** —— 守「失败也是成本」双本账。
4. **E2 gate19 verified 空填** —— 现所有源 `verified=待测`，不真跑一次就 active = 上线即崩。

## 四、新坑入库规范（持续补充）

### 4.1 何时入库
- 接入新源时发现本表未覆盖的风险
- 线上事故复盘出的成本/合规/可用性问题
- 对策落地后发现的次生坑（如 K 类）

### 4.2 入库步骤
1. **定类选前缀**（C/M/F/W/D/L/U/E/Q/K），取该前缀下一个序号（如新成本坑 = C9）
2. 填五列：触发 / 后果 / 对策 / 现状（🔴/⚠️/📋/✅）/ 主对策归口
3. §五 变更记录追一行，升 **patch**（v1.0→v1.1）
4. 若催生新对策机制 → 同步进 [埋点设计](probe-cost-metering-design-v1.0.md) 或 [动态管控设计](probe-data-dynamic-governance-design-v1.0.md)
5. 该坑被对策真正覆盖并实测 → 现状列改 ✅ 并注接入日期（不删条目，留演进痕迹）

### 4.3 现状列状态机
```
🔴 代码缺口  ──对策落码──▶  ⚠️ 接入时验证  ──S1真测通过──▶  ✅ 已防(注日期)
📋 合规已声明 ──接入时复核──▶  ✅ 已防
```

### 4.4 新坑模板（复制填写）
