# probe 数据源运行时架构 · 重设计（高效 · 准确 · 安全 · 降本）v1.1

> 日期：2026-06-10 · 性质：把分散的数据源设计(选型/编排/验证/合规/成本/缓存)**重新编排成一个统一运行时**，使四目标在同一架构下协同运转。
> **v1.1 智能化升级(2026-06-10)**：在 v1.0 规则版四引擎之上加 §八「**智能控制层**」——分层智能(规则守底线·学习提效率) + Meta-Controller 元控制器 + MAPE-K 学习闭环，让四引擎自适应、自学习、预测性决策，**系统越用越高效/准确/省钱**。
> 关系：本文是**运行时控制平面**设计——不推翻任何现有设计文档，而是把它们归位到四引擎、串成一个请求的生命周期。

## 0. 一句话

从「**一堆各管一摊的设计文档**」→「**一张源能力表驱动的四引擎统一控制平面**」。四引擎(降本/高效/准确/安全)读同一张表、串在一个请求生命周期里，于是**四目标不再 trade-off，而是相互增强**。

---

## 一、现状诊断：四目标分散 + trade-off 误区

| 目标 | 现有设计(已齐全) | 问题 |
|------|----------------|------|
| **降本** | 成本埋点 · 选型价值目录(Governor 概念) | 散点·无统一选源决策入口 |
| **高效** | 编排引擎(并发/限流/对冲) · 缓存层 | 与选源/验证脱节 |
| **准确** | 质量评测 · 监测雷达 · 8闸验证 · gate19 去重 | 验证孤立·不反哺选源 |
| **安全** | 隐私合规工程 · API风险清单 · 永不代爬铁律 | 合规判定靠人工·不在运行时强制 |

**两个核心病灶：**
1. **无统一控制平面**：四套设计各自为政，一个请求进来没有一条贯穿的生命周期把它们串起来。
2. **trade-off 思维**：默认「要准确就慢、要降本就不准」——**没有系统性利用四目标之间的协同点**(见 §五)。

**根因**：缺一张「**四引擎都读的源能力表**」。现在源元数据散在源卡(方法论)、价值目录、ledger、reliability(监测)四处，决策无法协同。

## 二、重设计核心：统一源能力价值表（SCT · 四引擎的共享大脑）

把分散的源元数据**合并成一张运行时表**，每个源四维标签，四引擎各读各维 → 一处更新、四处协同：

```yaml
# Source Capability Table (SCT) — 每个源一行·四维
source_id: groq-llama-3.3
# ── 成本维 (Governor 降本引擎读) ──
cost:        { tier: free, unit_price: 0, metering: 按次, cache_ttl: 3600 }
# ── 性能维 (Orchestrator 高效引擎读) ──
perf:        { latency_p50: 200, latency_p95: 800, rate_limit: {rpm: 30}, hedging_eligible: true, degradable: true }
# ── 可靠维 (Validator 准确引擎读) ──
trust:       { reliability: 0.92, freshness_window: 86400, upstream: groq, dedup: primary }
# ── 合规维 (Guardian 安全引擎读) ──
safety:      { license: apache-2.0, persist_policy: normal, crawl: clean, pii: false, gate: ai-deal-gate }
status: active   # cataloged → vetting → active
```

> SCT = [研究方法论 §3 机器可读源卡] + [选型价值目录] + [ledger 状态] + [监测 reliability] 的**运行时合并视图**。是本架构的地基。

## 三、四引擎（各司一目标 · 共读 SCT）

| 引擎 | 目标 | 读 SCT | 核心机制 |
|------|------|--------|---------|
| **Governor**（降本） | 花最少的钱 | 成本维 | 缓存命中检查 → 免费源优先阶梯 → 不够才付费(成本门) → R1 授权门 → 超额降级(付费→免费→缓存→占位) |
| **Orchestrator**（高效） | 最快出结果 | 性能维 | Scatter-Gather 并发 + per-source 令牌桶限流 + 关键信息对冲(仅免费源冗余取最快) + 流式增量 + 超时预算下放 |
| **Validator**（准确） | 结论可信 | 可靠维 | 多源交叉(独立源才算多票) + 源可靠度加权 + 新鲜度门 + 8闸 + 对抗证伪 |
| **Guardian**（安全） | 不出事 | 合规维 | **两次出场**：① 预检(合规门/PII 判定·挡违规源) ② 落库门(persist_policy·敏感→ephemeral) + 凭据隔离 + license 门 |

## 四、请求生命周期（四引擎在六环节协同）

```
              ┌─────────────── 共享大脑：SCT 源能力表 ───────────────┐
              │  成本维   性能维   可靠维   合规维                    │
              └──┬────────┬────────┬────────┬────────────────────────┘
   MetaAsk 澄清意图 │        │        │        │
        │          ▼        │        │        ▼
        ├──▶ ① Guardian 预检 ─────────────────┐  安全先行：合规门(永不代爬/灰产筛)+PII判定 → 挡掉违规源
        │                                      ▼
        ├──▶ ② Governor 选源 ◀── 成本维+可靠维   降本：查缓存命中 → 免费源阶梯 → (覆盖/置信不足)付费门
        │                                      ▼
        ├──▶ ③ Orchestrator 采集 ◀── 性能维     高效：并发+限流+对冲+流式 → 写缓存(带 source_version)
        │                                      ▼
        ├──▶ ④ Validator 验证 ◀── 可靠维        准确：多源交叉+可靠度加权+新鲜度门+8闸
        │                                      ▼
        ├──▶ ⑤ Guardian 落库 ◀── 合规维         安全：persist_policy(敏感→ephemeral禁PG)
        │                                      ▼
        └──▶ ⑥ 反馈回流 ──▶ 更新 SCT 可靠维      准确率/纠错 → reliability 在线修正 → 下次选源更优
                                               ▼
                                            交付(极速版/深度版)
```

**数据脊柱(PG+Redis)横向支撑全环节**：Redis 存缓存/限流令牌/任务态，PG 存可落库结论 + SCT + 成本台账。

## 五、四目标协同效应（反 trade-off · 本架构的灵魂）

**关键论证：同一个机制同时服务 ≥2 个目标 → 四目标相互增强，不是此消彼长。**

| 机制 | 高效 | 准确 | 安全 | 降本 |
|------|:----:|:----:|:----:|:----:|
| **缓存层(带 source_version)** | ✅ 零延迟命中 | ✅ 版本失效防陈旧污染 | — | ✅ 不重复付费 |
| **源可靠度加权** | ✅ 少等慢/差源 | ✅ 可靠源优先 | — | ✅ 少重试少补单 |
| **合规门前置** | ✅ 不采无效源 | — | ✅ 挡违规 | ✅ 灰产源不浪费调用 |
| **免费源优先阶梯** | — | — | ✅ 开源自托管可控 | ✅ 零成本 |
| **独立性去重(gate19)** | ✅ 不重复采同源 | ✅ 同源不算两票 | — | ✅ 省调用次数 |
| **对冲(仅免费源冗余)** | ✅ 取最快返回 | — | — | ✅ 免费才冗余·不烧钱 |
| **persist_policy(ephemeral)** | ✅ 不写库更快 | — | ✅ 敏感不落库 | ✅ 省存储 |

> **唯一的真 trade-off**：「**深度 vs 成本**」(查得越深越贵越慢)。本架构把它**显式收口到 Governor 的档位开关**——极速版(免费源兜底·秒级)/ 深度版(付费源+8闸·分钟级)，由用户付费档/blast 决定，而非散落在各处隐性权衡。

## 六、与现有设计文档的映射（归位 · 不推翻）

| 现有文档 | 归位到 | 角色 |
|---------|-------|------|
| 选型价值目录 / ledger | **SCT 成本维 + 状态** | 共享大脑 |
| 编排引擎 / 并发需求 | **Orchestrator** | 高效引擎 |
| 数据脊柱(PG+Redis) | **横向支撑** | 缓存/落库底座 |
| 质量评测 / 监测雷达 / 8闸 / gate19 | **Validator + 反馈回流** | 准确引擎 |
| 隐私合规 / 风险清单 / 三合规门 | **Guardian** | 安全引擎 |
| 成本埋点 | **Governor + PG 台账** | 降本引擎 |
| speed-depth-tiering | **Governor 档位开关** | 深度 vs 成本收口 |

> 本重设计 = **控制平面层**，把上述组件从「平行文档」变成「一个请求里协同的引擎」。

## 七、落地优先级（MVP 运行时 → 完整体）

**M0 · 零成本闭环先跑通**(用 D/E/I 域免费源验证全链路)：
1. 建 **SCT 表**(合并源卡，先填免费源)
2. **Guardian 合规门**(永不代爬/灰产筛·硬门)
3. **Governor 免费源阶梯**(免费兜底·先不接付费)
4. **缓存层**(Redis·带 source_version)
5. 简单 Scatter-Gather 并发

**M1 · 加准确**：Validator 多源交叉 + 可靠度加权 + 新鲜度门 + 反馈回流。

**M2 · 加降本深度**：Governor 付费门 + R1 授权 + 成本台账 + 档位开关(极速/深度)。

**M3 · 加高效极致**：对冲 + 流式 + 超时预算下放 + 8闸完整。

> 纪律：**安全门(Guardian)从 M0 就是硬门**——降本/高效可以渐进，合规不能打折。

## 八、智能化升级（v1.1）：从「规则驱动」到「自适应学习」

> v1.0 是**静态协同**(规则写死的四引擎)。v1.1 加一个**智能控制层**，让协同随数据**自我进化**——但有所为有所不为。

### 8.1 第一原则：分层智能（规则守底线 · 学习提效率）

**不是所有环节都该智能——分清楚才是真智能：**

| 类别 | 用什么 | 为什么 | 环节 |
|------|--------|--------|------|
| **守底线**(必须可审计) | **确定性规则** | 合规出事不可解释 = 灾难；必须可追溯、可复现 | Guardian 合规门 · persist_policy · license · 永不代爬 |
| **提效率**(越用越好) | **智能学习** | 选源/调度有海量反馈信号，适合自适应 | Governor 选源 · Orchestrator 调度 · 验证强度 · 缓存 · 深度档 |

> **🔴 智能化铁律**：智能**只能让 Guardian 拦得更多，不能让它放行更松**——智能识别新灰产/PII → 加拦截；但**规则硬门永不被概率模型绕过**(永不代爬不是"95% 不代爬")。安全是规则的，不是学习的。

### 8.2 Meta-Controller 元控制器（智能大脑）

在四引擎之上加一个智能决策层，统一驱动：

```
输入：查询特征(类型/blast/赛道/置信度需求) + SCT 源能力表 + 历史 outcome
  ↓  [Meta-Controller 智能决策]
输出：选源策略 · 编排参数 · 验证强度 · 深度档 · 缓存决策
  ↓  驱动四引擎执行
反馈：任务 outcome(命中/质量/成本/时延/用户纠错) → 回流学习 → 更新 SCT + 策略权重
```

### 8.3 四引擎的智能化

| 引擎 | v1.0 规则版 | v1.1 智能版 |
|------|------------|------------|
| **Governor** 选源 | 固定免费阶梯 | **期望效用评分** `U = 命中率×质量 ÷ (成本×时延)` + **contextual bandit** 平衡探索新源/利用好源 |
| **Orchestrator** 调度 | 固定并发/限流 | **预测时延**动态调并发/对冲触发/超时预算 + 限流自适应 |
| **Validator** 验证 | 固定 8 闸 | **LLM-judge + 异常检测** + **验证强度自适应**(高 blast/低 reliability 才加重，不需要时不浪费) |
| **Guardian** 合规 | 关键词规则门 | 灰产/PII **智能分类器增强**，但**规则硬门兜底**(智能只增拦截) |

### 8.4 学习闭环（MAPE-K · 越用越准/省/快）

```
监测(Monitor) ── 每次任务 outcome：命中?质量分?花多少钱?多快?用户纠错?
   ↓
分析(Analyze) ── 哪个源/策略表现好坏？源可靠度是否漂移？
   ↓
规划(Plan)    ── 调 SCT 权重(reliability/latency/cost 在线更新) + 选源策略
   ↓
执行(Execute) ── 下次任务用新策略
   ↓
知识(Knowledge)─ SCT 自我精化 → 系统越用越优
```

> 这是 v1.0「反馈回流」环节的智能化深化：不只更新 reliability，而是**整个选源/调度策略在线学习**。

### 8.5 五个关键智能机制

1. **Contextual Bandit 选源**：把「选哪个源」建模为多臂老虎机，自动学每类查询的最优源组合，平衡 explore(试新源) / exploit(用已知好源)——避免人工调参，自动适应源的变化。
2. **智能深度档界定**：系统按查询的 blast/置信度需求**自动判定**该用极速版还是深度版(而非用户手选)——对齐 [speed-depth-tiering](probe-speed-depth-tiering-v1.0.md) 的「智能界定」。
3. **语义级智能去重**：用 embedding 相似度判断多源是否同源(不只靠 SCT 的 upstream 字段)——比 gate19 静态图谱更细，防"换皮同源"算两票。
4. **预测性缓存保温**：预测哪些查询会复现，主动预取/延长 TTL——高效+降本动态最大化。
5. **源健康预测**：从历史限流/失效模式预测源何时会挂，提前切换——把被动降级变主动避让。

### 8.6 智能化如何放大「四目标协同」

v1.0 是固定协同，v1.1 让协同**自我优化**：
- **Bandit 选源**一次决策同时优化 成本+质量+时延 → **降本+准确+高效三合一**，且权重随反馈自调
- **自适应验证强度**：只在 blast 高/可靠度缺口大时加重验证 → **准确不牺牲高效/降本**
- **预测缓存+源健康预测**：把"事后补救"变"事前避让" → 高效/降本上限随数据抬高

> 结论：**v1.0 让四目标不冲突，v1.1 让四目标随数据持续逼近最优**。

### 8.7 智能化落地（接 §七 · 智能是 M1+ 增量）

| 阶段 | 智能化程度 |
|------|-----------|
| **M0** | **纯规则版**(不碰智能)——先有可工作的确定性兜底 |
| **M1** | 引入**反馈学习**：SCT 在线更新 reliability/latency/cost |
| **M2** | **Bandit 选源** + 智能深度档界定 |
| **M3** | **LLM-judge 验证** + 预测缓存 + 源健康预测 + 语义去重 |

> 🔴 纪律：**智能化永远要有规则版兜底**——模型冷启动/失效/置信不足时，自动回落到 M0 规则版(降级永不拒服务)。智能是锦上添花，规则是雪中送炭。

## 附：一句话总结四目标怎么同时拿

**SCT 一张表**(四维元数据) + **四引擎共读** + **缓存与可靠度反馈两个飞轮** → 选对源(降本)、并发取数(高效)、交叉验证(准确)、合规落库(安全)在**一个生命周期里一次完成**，靠协同机制让四目标相互成就，而非互相牺牲。
