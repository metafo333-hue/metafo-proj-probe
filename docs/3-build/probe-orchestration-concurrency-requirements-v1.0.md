# probe · 多赛道并发编排与时延优化 · 需求规格 v1.0

> 日期：2026-06-10 · 性质：probe 调度/编排层（单任务多赛道·多 API 协同）需求规格
> 背景：一个情报任务会拆成多个**赛道组合**（数据源轨）+ 每赛道多个 **API/数据源**，需要一套编排引擎解决「怎么高效出结果、怎么协同合成、怎么分配任务、怎么压总时长、要不要分布式」。

## 〇、需求一句话

> 让 probe 在处理单个情报任务时，把**多条数据源赛道 × 多个 API** 以最优的并发/依赖顺序跑起来，慢源不拖累整体，结果能交叉合成成一份可信结论，并把端到端时延压到档位预算内——软件编排为主、基础设施就近兜底。

## 一、问题定义（把口语需求结构化）

一个 probe 任务从下单到出结论，会经历：

```
任务 → 任务分解 → 选赛道(N条) → 每赛道选 API(M个) → 并发取数 → 验证(8闸) → 合成(L4) → 交付
         │            │             │              │           │          │
        意图        registry     能力注册表      编排引擎     源无关     LLM 归纳
```

口语需求里的四个真问题，逐条对应：

| 你的原话 | 拆出的工程问题 | 归属条目 |
|---------|--------------|---------|
| 「调用多个赛道组合和多个 API，怎么增加出结果的效率」 | 并发执行模型 + 时延优化 | R3 / R4 |
| 「相互合作合成方案」 | 多源结果合成 + 冲突消解 | R5 |
| 「怎么分配任务，减少总体时长」 | 任务建模(DAG) + 调度分配 | R1 / R2 / R4 |
| 「是否分布式或同步，软件到硬件」 | 架构选型 + 基础设施层 | R8 / R9 |

## 二、核心目标（量化，可验收）

| 目标 | 极速版 | 深度分析版 | 验收方式 |
|------|--------|-----------|---------|
| **T1 端到端时延** | P50 ≤ 8s · P95 ≤ 20s | P50 ≤ 90s · P95 ≤ 240s | 压测打点 |
| **T2 并发加速比** | 多赛道并发相对串行 ≥ 3× | ≥ 5× | 串/并对照 |
| **T3 慢源隔离** | 单赛道超时不影响其余赛道交付 | 同 | 注入慢源测试 |
| **T4 部分结果可用** | 超预算时用已到结果出「未全验」结论 | 出 partial + 标注待补 | 超时演练 |
| **T5 成本/限流不破** | 0 次 429/配额超限导致任务失败 | 同 | 限流注入 |
| **T6 合成正确性** | 多源冲突时按置信度加权且留痕 | 对抗证伪存活 | 冲突样例集 |

> 上述阈值为**待标定初值**，Sprint1 压测后回填真值。

## 三、需求条目

### R1 · 任务建模：DAG 分解（编排的地基）

- **R1.1** 每个 probe 任务编译为一张 **DAG（有向无环图）**：节点 = 一次「赛道/API 取数」或「验证/合成」步骤，边 = 数据依赖。
- **R1.2** 节点分两类依赖关系，决定能否并发：
  - **独立节点**（无上游依赖）→ 必须并发（如「百科赛道」「搜索赛道」「新闻赛道」同时打）。
  - **依赖节点**（上游产物是本节点入参）→ 按拓扑序串行（如先「搜索拿到实体 ID」→ 再「企业库查该实体详情」）。
- **R1.3** DAG 由**场景模板 + 数据源 registry 自动生成**，不写死：换模板/换源只改声明，编排引擎不动（呼应 L1-L4 源无关铁律）。
- **R1.4** 每个节点携带元数据：`赛道id · api id · 预估时延档 · 成本 · 限流组 · 是否可降级 · 超时预算`。

### R2 · 任务分配与调度（怎么分）

- **R2.1** **赛道优先级排序**：编排器按 `(信息价值密度 ÷ 预估时延 ÷ 成本)` 给赛道打分，高分赛道优先排进并发波次。
- **R2.2** **并发度分级控制**：
  - 全局并发上限（防把本机/出口打满）。
  - 每数据源/每限流组独立并发上限（防单源 429）。
  - 用**信号量/令牌桶**实现，而非无限扇出。
- **R2.3** **波次调度（wave scheduling）**：DAG 按拓扑层切成波次，同波次内全并发，波次间按依赖推进；不等整波全完，**就绪即推进下一节点**（pipeline，不设硬 barrier）。
- **R2.4** **任务隔离**：不同 probe 任务之间资源隔离（一个大任务不饿死小任务），用任务级配额 + 优先级队列。
- **R2.5** **档位驱动深浅**：极速版只排「快赛道 + 单轮」，深度版排「全赛道 + 付费源 + 交叉轮次」——同一编排器，参数化。

### R3 · 并发执行模型（扇出/扇入）

- **R3.1** **IO 密集优先用异步协程**：API 调用本质是网络 IO，单进程 `async/await` + 协程池即可吃满并发，不必上多进程/多机（先软件后硬件）。
- **R3.2** **扇出（fan-out）**：一任务 → N 赛道 → 每赛道 → M API，三级扇出并发下发。
- **R3.3** **扇入（fan-in）**：结果回流到合成器，支持两种回流：
  - **栅栏式（barrier）**：等本波全到再合成——仅当合成必须看全集时用（如去重/全局排序）。
  - **流式（streaming）**：每到一个结果就增量并入——默认模式，降低尾延迟。
- **R3.4** **连接复用**：HTTP keep-alive + 连接池 + DNS 缓存，避免每次 API 重建连接。
- **R3.5** **幂等与重试**：每节点可安全重试（带退避），重试不污染合成结果。

### R4 · 时延优化策略（压总时长，核心）

- **R4.1** **超时预算下放**：任务总预算 → 按档位切给各波次 → 切给各节点。节点超预算即被 cancel，不无限等。
- **R4.2** **慢源不阻塞交付**：达到「最低可信源数」即可触发合成，慢源结果**后补增量更新**（先出结论，再补充）。
- **R4.3** **推测/冗余执行（hedging）**：对关键信息，同时打**多个等价源**取最快返回的（如三个搜索源并发，谁先回用谁），用冗余换尾延迟——仅对低成本免费源开，付费源不冗余（控成本）。
- **R4.4** **分级缓存**：
  - L1 结果缓存（同查询近期命中直接返回，TTL 按数据时效性分级：百科长 TTL、舆情短 TTL）。
  - L2 数据源原始响应缓存（不同任务复用同一源结果）。
  - 缓存键含「源版本」，源升级即失效。
- **R4.5** **预热与预取**：高频赛道/热点实体后台预取，命中即秒回。
- **R4.6** **早返回（early-return）**：极速版「确定性自评」达高确定即停止追加赛道，不做无谓深挖（对齐 speed-tiering 信号 C）。

### R5 · 多源结果合成与冲突消解（相互合作合成）

- **R5.1** **统一中间表示**：各赛道结果归一化为统一 schema（实体/事实/来源/时间/置信），再进合成器（源无关）。
- **R5.2** **去重与实体对齐**：跨源同一事实合并，保留全部出处（用于溯源闸）。
- **R5.3** **交叉印证**：同一断言多源一致 → 置信度上调；单源孤证 → 标注「待证」。
- **R5.4** **冲突消解**：多源矛盾时按 `源权威度 × 时效 × 一致票数` 加权，**保留少数派观点**（深度版需呈现反方），不静默丢弃（对齐 8闸·矛盾闸）。
- **R5.5** **合成可由 LLM 承担但受闸约束**：L4 用 LLM 把碎片炼成结论，但事实必须可回溯到源（禁 LLM 凭空补全）。
- **R5.6** **增量合成**：配合 R3.3 流式，结论随新结果到达而演进，前端可见「证据在增长」。

### R6 · 限流 / 配额 / 成本治理

- **R6.1** **每源限流模型**：登记每个 API 的 QPS/日配额/并发上限到能力注册表，编排器据此调度（令牌桶 per-source）。
- **R6.2** **配额预算门**：付费源调用前过成本门（对齐 cost-metering），超预算降级到免费源或停。
- **R6.3** **优雅退避**：收 429/限流 → 指数退避重排，不硬重试；多次失败 → 该源本任务内熔断降级。
- **R6.4** **成本-价值权衡**：付费源仅在「免费源不足以达成档位置信」时才触发（按需升级，对齐 source-selection ROI 顺序）。

### R7 · 容错与降级

- **R7.1** **单赛道失败隔离**：任一赛道/API 失败不抛整任务，降级为「该维度缺失」并标注。
- **R7.2** **最低可信底线**：定义每档位「最少成功赛道数/源数」，低于底线才判任务失败。
- **R7.3** **降级链**：付费源失败 → 免费等价源 → 缓存兜底 → 标注缺失。
- **R7.4** **部分交付**：超预算/部分失败时输出 partial 结论 + 明确边界标注（对齐极速版「诚实标注未全验」）。

### R8 · 架构选型：分布式 vs 同步（要不要分布式）

- **R8.1 选型原则**：**先单机异步，后分布式**。probe 取数是 IO 密集，单进程协程在中小并发下时延最低、复杂度最小；分布式是**吞吐/隔离/就近**到瓶颈后才上。
- **R8.2 三层演进路线**（按需逐级，不一步到位）：

| 阶段 | 形态 | 适用 | 代价 |
|------|------|------|------|
| **S1 单机异步** | 单进程 `asyncio` + 协程池 + 信号量限流 | 任务内多赛道扇出·中小并发 | 最低·单点 |
| **S2 队列 + worker** | 任务入队（Redis queue / Arq / Celery），worker 池横向扩 | 任务间高吞吐·长任务·隔离·失败重投 | 中·需消息中间件 |
| **S3 就近分布式** | 按数据源地理位置分 worker 池（海外源→海外节点）+ 中心合成 | 跨地域付费源·抗封·降网络往返 | 高·跨机编排 |

- **R8.3 推荐落地**：**单任务内 = S1 异步扇出（低延迟）；任务间 = S2 队列调度（吞吐+隔离）**。即「任务级分布式 + 任务内协程」的混合，兼顾延迟与扩展。
- **R8.4 状态外置**：worker 无状态，共享状态（缓存/限流计数/任务态）走 Redis/PG，禁进程内全局可变状态（对齐 R14）。
- **R8.5 同步 vs 异步交付**：极速版**同步阻塞返回**（用户等几秒）；深度版**异步任务**（提交→轮询/推送结果），前端进度可见。

### R9 · 硬件 / 基础设施层（软件到硬件）

- **R9.1 部署归属**：probe 是非交易共用业务，**禁上交易机（boss8001-a/b）**；落 ufo2（共用内部平台）或独立节点（对齐 server-roles 串台红线 T1/T2）。
- **R9.2 算力画像**：L2 采集 = IO 密集（吃网络/连接数，不吃 CPU/GPU）；L4 合成 = LLM 推理，**走 LiteLLM 路由**（不在 probe 本机起大模型）。即 probe 主机要的是**高并发网络 + 内存缓存**，不是 GPU。
- **R9.3 网络出口**：
  - 连接池 + keep-alive 复用（软件层先榨干）。
  - **代理/出口 IP 池**：抗封、抗地域限制（部分源对单 IP 限频）。
  - 海外付费源就近：评估海外采集 worker（注意**不得复用东京交易机**，需独立非交易节点）。
- **R9.4 缓存基础设施**：Redis 作共享缓存 + 限流计数 + 任务队列三合一（信号总线类，注意与 boss8001-b 的交易 Redis 物理隔离，禁混用）。
- **R9.5 存储**：任务态/结果落 PG（对齐 R28 业务数据入 PG）；原始大响应可对象存储/临时缓存，不塞 PG 主表。
- **R9.6 弹性**：worker 池可按队列积压自动伸缩（S2/S3 阶段），峰值扩、谷期缩。

### R10 · 可观测性（没观测就没法优化时延）

- **R10.1** 每节点打点：赛道/API、排队时长、执行时长、命中缓存否、成功/降级/失败、成本。
- **R10.2** 端到端火焰图/瀑布图：定位是哪条赛道是关键路径（拖慢总时长的瓶颈）。
- **R10.3** 关键指标看板：P50/P95 时延、并发加速比、各源成功率/限流率、缓存命中率、成本/任务。
- **R10.4** 慢任务回放：超 P95 的任务可回放其 DAG 调度轨迹，用于持续调优。

## 四、候选架构方案对比（供拍板）

| 维度 | A · 纯单机异步 | B · 异步 + 任务队列（推荐） | C · 全分布式就近 |
|------|--------------|--------------------------|----------------|
| 任务内并发 | 协程扇出 | 协程扇出 | 协程扇出 |
| 任务间扩展 | 单进程上限 | worker 横向扩 | 跨地域 worker |
| 时延 | 最低 | 低（队列有微小排队） | 跨机有网络开销 |
| 吞吐 | 受限 | 高 | 最高 |
| 复杂度/成本 | 最低 | 中 | 高 |
| 就近付费源 | 否 | 否 | 是 |
| 适用阶段 | MVP/验证 | **主力形态** | 规模化后 |

> 建议：**Sprint1 落 A 验证编排正确性 → Sprint2 升 B 作主力 → 付费源地域瓶颈出现再评估 C**。不为未到的规模提前付分布式复杂度税。

## 六、非功能性约束

- **N1 源无关**：编排器对具体数据源零硬编码，换源只改 registry。
- **N2 无进程内可变状态**：多 worker 共享态走 Redis/PG（R14）。
- **N3 数据落位合规**：业务数据入 PG（R28）；probe 不上交易机（T1/T2）；Redis 与交易总线隔离（T4）。
- **N4 成本可控**：付费源按 ROI 顺序、按需触发、过成本门。
- **N5 诚实边界**：部分结果/降级必须显式标注「未全验/某维度缺失」。
- **N6 可回溯**：每条结论可追到源（喂溯源闸）。

## 七、待元东方拍板项

1. **架构起点**：直接上 B（异步+队列）还是先 A（纯单机异步）验证？（建议 A→B 渐进）
2. **海外付费源就近**：是否值得为 DataForSEO/Keepa 等海外源建独立海外采集节点？还是先接受跨洋往返时延？
3. **时延目标**：第二章 T1 的 P50/P95 初值是否认可，还是按你的产品体感重定？
4. **冗余执行成本**：R4.3 对免费源开 hedging（冗余请求换速度）是否接受其额外调用量？
5. **极速版同步阻塞时长上限**：用户最多愿意同步等几秒（超过转异步）？
6. **消息中间件**：S2 队列用 Redis 系（Arq）还是 Celery？（建议 Redis/Arq，轻、与缓存复用同一 Redis 实例）
