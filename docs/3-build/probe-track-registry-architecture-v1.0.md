## 0. 一句话

把 5 业务域（A–E）+ 金融 F + 元惠 G + 任务系统 H **全部登记进同一张 track registry**，每条赛道带 `type / tier / weight / presentation` 元数据。「第六、第七、第八个」不再游离体系外，而是注册表里 `tier=flagship` 的几条——**同表共存、数得清，特殊性靠字段体现，不靠两套并列维度**。

## 1. 背景：为什么要统一注册表

probe 原有两套切法并存，导致「这是第几个域」数不清：

| 维度 | 切法 | 成员 | 问题 |
|------|------|------|------|
| **业务域**（横向能力） | 按情报类型 + 客群 | A 自媒体 / B 商业 / C 尽调 / D 调研 / E 核查 | 通用能力，任何行业都能用 |
| **垂直赛道**（纵向行业） | 按行业深耕 | 金融 F / 元惠 G / 任务 H | 复用横向能力 + 叠专属深耕，价值更高但无容器装 |

**根因**：垂直赛道 = 在一个行业里把多个横向能力**打包成套** + 叠专属信息域/验证闸/商业模式。它价值高，因为是「成套解决方案」而非「单一能力」。但它既不是第 6 个并列业务域，也不该游离体系外。

**解法**：统一成一张 `tracks` 注册表，`type` 区分横纵，`tier` 标记旗舰，`weight` 驱动资源倾斜，`presentation` 驱动展示差异化。**加赛道、调权重、改展示、升降级，全是改数据不改架构。**

## 2. 三层架构（schema）

### 2.1 分类层：`type` + `tier`

| 字段 | 取值 | 含义 |
|------|------|------|
| `type` | `horizontal`（通用业务域） / `vertical`（垂直行业赛道） | 横向能力切法 vs 纵向行业切法 |
| `tier` | `standard` / `flagship` / `incubating` | 重要性等级；flagship = 单独深耕、享差异化待遇 |

### 2.2 权重层：`weight`（一个总开关驱动 5 路倾斜）

`weight`（0–100）是旗舰赛道「组合调用权重不同」的落地点，同时驱动：

| 权重维度 | 普通业务域（standard） | 旗舰赛道（flagship） |
|---------|----------------------|---------------------|
| **采集权重** | 默认源集 + 通用业务域源 | 默认调用**专属信息域 + 更深档位** |
| **验证权重** | 验证层 闸0-7(双审8闸) | **专属加严闸**（金融赛道准入 finance-gate-profile（此为赛道准入 verify_profile，**同名异指**于通用双审8闸·见 SSOT §3 门对照·建议后续改称 finance-gate-profile）/ 元惠防虚标价闸） |
| **编排权重**（MetaFlow） | 按需被组合 | **可作默认组合锚点 · 推荐排序靠前 · 可反向定义组合链** |
| **资源权重**（R1 付费源） | 排队按 ROI | **优先获付费源授权额度** |
| **商业权重** | 走平台统一档位 | **独立商业模式**（F 按件 / G CPS 返利 / H CPS 拉新） |

### 2.3 展示层：`presentation`（驱动视觉 4 件，全部数据驱动）

承载「特殊展示 / 暗示 / 提醒 / 快捷入口」，UI 读字段渲染，**不写死、不另起**，复用现有 hub 底座：

| 需求 | 字段 | 复用的现有底座 |
|------|------|---------------|
| **特殊展示** | `badge` + `prominence` | hub 看板（HubBoard）+ 颜色走 `tokens-brand.css`（新增 `--mfc-flagship`） |
| **暗示** | `hint.affordance` / `combo_hint` | 卡片角标 + MetaFlow 组合推荐 |
| **提醒** | `reminders[]` | **复用 hub-whatsnew `changelog.json` 提醒系统**（红点/脉冲/callout 现成） |
| **快捷入口** | `quick_entry[]` | hub registry 渲染 + 导航路由 + MetaFlow preset |

### 2.4 完整 schema 示例（旗舰条目）

```yaml
tracks:
  - id: G-deal
    name_cn: 元惠 ;  name_en: MetaDeal
    type: vertical ;  tier: flagship ;  weight: 85       # weight 算法见 §8.4
    status: incubating                                   # 生命周期见 §8.5
    primary_intent: 省钱                                  # 意图终点·边界归属见 §8.2
    owned_domains: [D15-促销与优惠] ;  shared_domains: [D9]   # D15 定义见 §8.3
    verify_profile: deal-pricefraud-gate ;  biz_model: CPS返利分佣 + 付费深探
    flagship_reasons: [C端高频刚需, CPS可变现, 防假促销护城河]
    audience: [C端省钱党, 小B促销监控] ;  pricing: 免费比价 + 付费蹲价提醒  # §8.8
    compliance:                                          # 合规红线见 §8.1
      gate: deal-compliance-gate
      redlines: [禁虚假比价, 禁失效券引流, 禁刷返利, 守联盟ToS]
      exclude_categories: [刷单返现, 资金盘返利]
    presentation:
      badge:      { label: 旗舰, icon: "⭐", color_token: "--mfc-flagship" }
      prominence: pinned                       # pinned置顶 / featured旗舰区 / normal
      hint:
        affordance: "深度分析版 · CPS返利"
        combo_hint: [Probe→Design, Probe×Ops雷达]
      reminders:
        - { type: calendar,  desc: 大促日历预警, source: changelog.json }
        - { type: subscribe, desc: 可订阅价格雷达 }
      quick_entry:
        - { surface: hub-home, slot: featured-card }
        - { surface: nav,      path: /deal }
        - { surface: metaflow, preset: deal-combo }
```

## 4. 旗舰赛道深挖目录

> 深挖结构同构：每条旗舰 = **8 个特殊端口 × 三级目录（目录→分类→品类）× 交叉轴**。新增旗舰直接复制此骨架。

### 4.1 G · 元惠（消费省钱 · 优惠情报）

**8 个特殊端口（按省钱机制切）**

| # | 端口 | 分类（玩法） | 品类（子类型） | 数据源举例（⚠️待核实） |
|---|------|------------|--------------|---------------------|

| 3 | 折扣促销 | 限时/秒杀/清仓 | 限时折扣·秒杀·尾货清仓·特价专区 | 各平台促销位 |
| 4 | 返利 CPS | 购物返现/隐藏佣金 | 返利率·叠加返·提现门槛 | 返利网 / 一淘 / 高佣联盟 / 好省 |

| 返利兑现 | 返利率真实性、提现门槛/到账周期 |

## 8. v1.1 深度补强（八洞解决方案）

> 来源：v1.0 落地前完整性查漏，识别 8 个会导致「出事 / 打架 / 悬空」的洞。本章逐洞给深度解决方案，已回填 §2.4 schema 与 §3 注册表字段。

### 8.1 合规红线体系（洞①·灰产防火墙·最高优先）

**问题深度**：任务系统 H 所在的「任务/众包/拉新」生态，合规光谱从白到黑跨度极大——平台官方任务（白）→ 第三方众包（灰，混刷量刷单）→ 资金盘拉人头/刷单返利诈骗/批量薅羊毛黑产（黑）。probe 若不设红线，会踩**「为灰产/刷单引流」「帮助违规薅羊毛」「为诈骗平台导流」**三类法律 + 平台 ToS 红线（命中 R0.7 漏点④信任·监管）。

**解决方案：`compliance` schema 段（每条赛道必填）**

```yaml
compliance:
  gate: <profile-id>              # 准入合规门(立项前必过)
  redlines: [...]                 # 该赛道禁做清单
  exclude_categories: [...]       # 在端口品类层打 excluded 标记的黑名单品类
  data_boundary: <说明>           # 个保法数据边界
```

**三旗舰红线实例**

| 赛道 | 准入门 | 核心红线 | 排除品类（不采集/不呈现） |
|------|--------|---------|------------------------|
| F 金融 | finance-8gate（此为金融赛道准入 verify_profile，**同名异指**于通用双审8闸·见 SSOT §3 门对照·建议后续改称 finance-gate-profile） | 不荐股不导流不碰非持牌、6 红线（见 F 设计 §3.5） | 场外配资、非法荐股、虚拟币传销盘 |
| G 元惠 | deal-compliance-gate | 禁虚假比价、禁失效券引流、禁刷返利、守联盟 ToS | 刷单返现、资金盘返利 |
| **H 任务** | **task-compliance-gate** | **只做合规任务情报；禁为刷单/灰产/资金盘导流；禁教唆违反平台 ToS 薅羊毛；不收集任务参与者个人数据** | **刷单刷量、拉人头/传销、高额返利诱充、批量账号薅羊毛、博彩/资金盘任务** |

**赛道准入合规门（新赛道立项前必过 · 类比 R30 新服务上线检查清单）**：
① 数据是否公开合规获取（非代爬）② 是否存在为违规行为导流的风险 ③ 个保法最小必要 ④ 是否触碰持牌/资质红线 ⑤ exclude_categories 是否已在品类层落标记。**五问全过才允许 `status: incubating→building`。**

### 8.2 赛道边界裁定（洞②·串台红线）

**问题深度**：端口存在真实重叠 —— G「拼团砍价」vs H「分享裂变(助力砍价)」；F「个人理财/信用卡」vs G「金融消费优惠/信用卡」；H「消费下单任务」vs G「返利 CPS」。无裁定则采集重复、呈现打架。

**总原则：按「用户意图终点」归主赛道**（`primary_intent` 字段）。数据层可共享采集，**呈现层归唯一主赛道**。

| 重叠场景 | 共同动作 | 意图终点 → 主赛道 | 裁定 |
|---------|---------|------------------|------|
| 砍价/拼团 | 砍价 | 降低购买价 → **G 省钱** ／ 拿任务奖励 → **H 搞钱** | 同动作按目的分流 |
| 信用卡 | 信用卡情报 | 额度/征信/理财属性 → **F 投资** ／ 消费返现/折扣 → **G 省钱** | 按属性分层 |
| 下单返钱 | 消费返利 | 购物本身省钱 → **G** ／ 为完成任务拿佣金 → **H** | 按主目的归属 |

**裁定落地**：① 每条赛道声明 `primary_intent`；② MetaAsk 澄清意图时识别「终点」→ 命中主赛道；③ 数据采集层共享（同一 D9/D15/D16 源），呈现/计费归主赛道，避免双算。

### 8.3 信息域 D15 / D16 落真源（洞③·消除悬空引用）

**问题深度**：G 引用 `D15`、H 引用 `D16`，需在 `ledger.yaml` `domains:` 中确认已落定义。（真源 ledger.yaml v5 已收录 D1-D17，域映射真源=ledger.yaml tracks 段）**落 `tracks:` 段前须核验 ledger v5 中 D15/D16 定义完整。**

| 域 | 代号 | 域语义 | 代表真实源（举例·待 4-research 核实） | 合规 | 喂哪些赛道 |
|----|------|--------|--------------------------------------|------|-----------|
| 促销与优惠 | **D15** | 价格促销/券/折扣/返利/大促日历 数据 | 联盟开放平台券API · 比价源（慢慢买/什么值得买）· Keepa 历史价 · 各平台 promo 位 | ⚠️（联盟需资质·比价源核 ToS） | G 元惠 |
| 任务与激励 | **D16** | 平台任务系统/悬赏/激励规则 公开数据 | 各平台官方任务中心公开规则 · 合规众包平台开放接口 · 公开活动页 | ⚠️（仅公开规则·禁灰产源） | H 任务 |

> 接入纪律不变：走 §2 标准19 核验 + 合规判定，`status=active` 才放行（D15/D16 的 ⚠️ 源多数需 R1 授权或资质）。

### 8.4 weight 打分卡（洞④·权重有据可依）

**问题深度**：90/85/80 原为拍脑袋，新赛道会乱填。

**解决方案：四维各 0–25，合计即 weight（0–100）**

```
weight = 客单价潜力(0-25) + 需求频次规模(0-25) + 合规可控度(0-25) + 数据护城河(0-25)
```

| 赛道 | 客单价 | 频次规模 | 合规可控 | 数据护城河 | = weight |
|------|-------|---------|---------|-----------|---------|
| F 金融 | 23（高客单/企业付费） | 20 | 22（持牌边界清晰） | 25（付费专业源） | **90** |
| G 元惠 | 18（CPS+轻付费） | 25（全民高频） | 20（联盟 ToS 可控） | 22（比价/历史价壁垒） | **85** |
| H 任务 | 17（订阅+CPS） | 24（高频刚需） | 18（灰产风险需强门） | 21（任务聚合壁垒） | **80** |

> 合规可控度低会直接压低 weight —— 这让「合规风险」反向约束资源倾斜，是 8.1 红线的量化呼应。

### 8.5 status 生命周期（洞⑥·与 tier 正交）

**`status` 是生命周期，`tier` 是重要性，两轴正交**（一个 flagship 也可能还在 incubating）。

```
incubating(孵化/设计) → building(在建·过合规门) → active(上线) → paused(暂停) → deprecated(弃用) → retired(退役)
```

当前：A=active（锚点垂类已跑通）· B/C/D/E=building · F/G/H=incubating（设计完成待开工）。`status` 字段驱动 hub 看板的进度呈现与 `presentation` 是否生效（仅 active 出快捷入口）。

### 8.6 横向业务域 A–E 不空心（洞⑤·能力映射）

**问题**：只有 F/G/H 旗舰深挖了 8 端口，A–E 在注册表里没自己的目录。

**解决方案：A–E 不重做，做映射** —— horizontal 条目挂 `capabilities[]`，指向 design-v1 §5.1 的既有子场景（A1–A7 / B1–B6 / C1–C5 / D1–D5 / E1–E4，共 27 场景）。即：**横向域的「目录」= §5.1 场景表的注册表视图**，旗舰的「目录」= §4 的 8 端口深挖。两者在注册表里用 `type` 区分呈现，不混淆。验证层使用 闸0-7(双审8闸·见 audit-system-v1)，非旧 ①-⑥ 编号。

### 8.7 MetaAsk 意图 → 赛道路由（洞⑦）

输入经 MetaAsk 澄清后路由到赛道：
1. **特征匹配**：输入类型（链接/品类词/平台名/文档）+ 关键词 → 候选赛道集；
2. **意图终点判定**（§8.2 `primary_intent`）：省钱/搞钱/投资/核查/调研… → 收敛到主赛道；
3. **旗舰优先**：命中 flagship 时，高 `weight` 提升路由置信度，优先走旗舰深度档（专属信息域 + 加严闸）；
4. **多赛道命中** → 按 `weight` 排序，交 MetaFlow 生成组合链（如「比价 + 任务」= 元惠×任务组合）。

### 8.8 客群与定价轴并入（洞⑧）

把 G/H 接进 design-v1 §5.3 客群分层（`audience` + `pricing` 字段）：

| 赛道 | 主客群 | 定价模型 |
|------|-------|---------|
| G 元惠 | C 端省钱党（主）+ 小 B 促销监控 | 免费比价 + 付费蹲价提醒/全网比价 + CPS 返利分佣 |
| H 任务 | C 端搞钱党（主）+ B 端发包方 | 免费任务目录 + 付费任务情报订阅 + CPS 拉新分佣 |

> G/H 的「免费引流 + CPS 变现」模型与 A–F 的「按次/订阅」不同 —— 这是 §2.2 商业权重差异化的具体落点。
