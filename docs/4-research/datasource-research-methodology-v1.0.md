## 1. 系统特性 → 为什么是这个优先级（推导，非拍板）

probe 的三护城河 + 两铁律决定了源的排序，不是凭喜好：

| probe 系统特性 | 对数据源的硬要求 | 推导 |
|---------------|----------------|------|
| **解耦热插拔**（换源只改质量不改流程） | 源要可替换、可自托管、不被单点锁死 | → **开源自托管最优**（主动权在自己手） |
| **永不代爬**（铁律②） | 必须官方/开放/开源合法端口 | → 排除一切逆向/绕反爬源 |
| **API-First + 全自动**（L1 契约） | 必须能 API 化无人值守接入 | → 纯人工下载源降级或弃 |
| **数据源护城河**（专业可验证真材料） | 权威性、专业性、可溯源 | → **权威官方源质量最高**（金标准） |
| **抗污染验证**（多源交叉） | 源要多、要异构、要能互相验证 | → 三层都要有，靠数量+异构抗污染 |
| **成本可控**（Governor 免费兜底） | 免费优先、付费有门 | → 免费开源打底，付费综合服务按需 |

**结论优先级**（= 用户指定排序的系统性依据）：

```
层1 第三方开源 API（最优先·主动权+零成本+合规+可自托管）
  └ 不够 ──▶ 层2 第三方综合服务 API（覆盖广+省接入·但付费+单点依赖）
              └ 权威/深度不够 ──▶ 层3 其他自动化权威接口（权威金标准·但分散+需资质）
```

> 这条阶梯**同构于 Governor 选源**（免费兜底→按需升级），只是把它从「选哪个源」上升到「选哪类源」。

## 2. 三层选型优先级（核心·每层的方向/内容/审核）

### 层 1 · 第三方开源 API 接口（🥇 最优先）

- **定义**：开源项目提供、**可自托管**的 API。例：SearXNG（聚合搜索）· RSSHub（万物 RSS）· OpenSanctions/Yente（制裁名单）· AKShare（开源行情）· Docling/trafilatura（解析）· LibreTranslate · GDELT。
- **为何最优**：免费 · 自托管掌握主动权 · 无 ToS 封禁风险 · 天然热插拔 · 完全自动化 · 数据来源透明可审。**最贴 probe「解耦炼油厂」本质。**
- **调研方向（怎么找）**：GitHub topic / awesome-list（`awesome-<域>` · `<域>-api` · `self-hosted`）→ 按 star + 近 90 天 commit 活跃筛 → 看有无 `docker-compose`/`/api` 自托管文档。
- **调研内容（查什么）**：license（**必须商用友好** MIT/Apache/AGPL 评估）· 维护活跃度 · 自托管资源消耗（内存/算力）· API 稳定性 · 数据覆盖与时效 · 更新机制。
- **审核重点**：① license 是否允许商用 ② 自托管成本是否可控 ③ 项目是否会断更（单人项目慎用）④ 数据是否其自身也靠代爬（**上游污染要穿透审**）。

### 层 2 · 第三方综合服务接口（🥈 次优）

- **定义**：商业**聚合/一站式** API。例：Tavily/Exa（AI 搜索）· DataForSEO/SerpAPI（SERP/SEO）· TikHub（自媒体聚合）· Apify（通用抓取托管）· Keepa（电商价格）。
- **为何次优**：一个接口覆盖广、省去逐个对接 · 但**付费 + 单点依赖 + 受其 ToS 约束 + 数据来源不透明**。
- **调研方向**：产品对比评测 / G2 / 官方价格页 / 免费试用额度实测 → 横向比覆盖度与性价比。
- **调研内容**：覆盖范围 · 单价/限额/SLA · 数据**来源合法性**（它的数据哪来的？是否帮你背了代爬的锅）· 降级可行性。
- **审核重点**：① 性价比 ROI（vs 自建层1）② SLA 稳定性 ③ **数据来源合规性穿透**（综合服务最大暗坑）④ 单点依赖能否降级到层1/缓存。

### 层 3 · 其他自动化权威接口（🥉 权威补充）

- **定义**：官方/权威机构**开放 API**。例：政府开放数据（data.gov/国家统计局）· FRED（美联储）· YouTube Data API · GitHub API · Crossref/OpenAlex（学术）· 各平台官方开放平台 · 央行/交易所公开接口。
- **为何补充而非首选**：**权威性最高**（喂 AI 真材料的金标准、抗污染贡献最大）· 合规 · 但**分散**（每个单独对接）· 对接成本高 · 部分需资质申请。
- **调研方向**：官方开放数据门户 / 开放平台开发者中心 → 确认「有 API」而非「只有网页/下载」。
- **调研内容**：开放 API 文档 · 申请资质门槛 · 限额 · 字段权威度 · 更新机制 · 是否真自动化（API vs 仅 CSV 下载）。
- **审核重点**：① 权威背书（官方/一级源）② 申请门槛与周期 ③ **自动化可行性**（只有手动下载 → 降级或弃）④ 资质是否涉 R4。

## 3. 调研内容统一清单（每源必查 · = 能力价值目录字段）

每调研一个源，无论哪层，产出一条 [source-selection](../3-build/probe-source-selection-and-capability-registry-v1.0.md) 能力价值目录记录：

| 字段组 | 必填项 | 喂哪个子系统（v1.1·出处见 §8） |
|--------|--------|------------------------------|
| **身份** | 名称 · 层级(开源/综合/权威) · 官网 · repo · 接入域(D1–D16) · 赛道id | ledger / track registry |
| **能力** | 数据品类 · 覆盖范围 · 字段 · 时效 · 抗污染贡献 | 能力价值目录 / Governor |
| **接入** | API 形态(REST/GraphQL/SDK) · 认证 · 限额 · SLA | 适配器开发 |
| **成本** | 免费额度 · 单价(计量口径) · 自托管成本 | cost-metering 成本埋点 |
| **合规** | license · ToS · 数据来源合法性 · **是否代爬（含上游穿透）** | 三合规门 / risk-checklist |
| **自动化** | 全自动(API) / 半自动(需人工触发) / 不可自动(弃) | L1 契约 / 无人值守 |
| **🆕 编排适配** | 预估时延档(p50/p95) · QPS/日配额/并发上限(限流组) · 超时预算建议 · 是否可降级 · **hedging 资格(免费=可对冲/付费=禁)** | 编排引擎(需求 R1.4/R6.1/R4.3) |
| **🆕 持久化策略** | `persist_policy`(normal/**ephemeral**·人物OSINT敏感→禁落库) · 缓存TTL建议(L1结论/L2源响应) · ToS 留存限制 · `source_version` | 数据脊柱(PG+Redis) / 隐私合规 |
| **🆕 独立性图谱** | 底层真实数据源(源的源) · 同源关系(主入口/兜底/rejected) · 交叉验证独立性(同源不算两票) | gate19 §B9 去重图谱 / 8 闸验证 |
| **🆕 可靠度先验** | 权威分初值(冷启动先验) · golden 样本(3-5 条实测真值留存) | probe_source_reliability / 质量评测回归 |
| **决策** | 优先级层 · 状态(候选/核验中/沙箱实测/采纳/弃) · 弃用理由 | 全局 |

## 4. 调研审核：三道审核闸（源的「元审核」·过了才进标准19）

probe 连数据源本身都要审——这是「抗污染从源头做起」。**三闸全过才进标准19 接入门**：

| 闸 | 名称 | 判据 | 不过的处理 |
|----|------|------|-----------|
| **闸 A · 合规审核** | 源是否干净 | license 商用 ✅ · ToS 允许 ✅ · **非代爬（穿透上游）** ✅ · 数据来源合法 ✅ | 任一不过 → **直接弃**（不进调研下一步） |
| **闸 B · 自动化审核** | 能否无人值守接入 | 有稳定 API · 可程序化拉取 · 契合 L1 契约 | 仅人工下载 → 降级（人工补录）或弃 |
| **闸 C · 质量审核** | 数据是否可信 | 权威性 · 准确度 · 时效 · 抗污染贡献；**对抗证伪**（派证伪路核「真有此 API/真免费/真合规」，默认 refuted） | 证伪成立 → 打回重核或弃 |
| **🆕 闸 D · 系统适配审核（v1.1）** | 接进来后系统能不能用好 | ① 沙箱实测真调通（§9.1）② 编排元数据齐（时延/限流/超时实测非猜）③ persist_policy 判定（敏感→ephemeral）④ 独立性裁定（同源去重图谱归位）⑤ golden 样本留存 | 缺项 → 不得 `status=active`，停在 `cataloged` |

> 闸 C 的对抗证伪是 probe 抗污染特性在「选源」环节的落地：**不信调研者的一面之词**，官方文档实证才采信（R0.8）。
> 闸 D 是 v1.1 新增的「最大化满足系统要求」落点：**A/B/C 审的是「源好不好」，D 审的是「我们的系统接它接得顺不顺」**——四闸全过才算调研完成。

## 5. 实战决策树（Governor 选源查表）

```
任务来 → 查能力价值目录
  ├─ 层1 开源源能覆盖且质量够? ── 是 ▶ 用开源(零成本·首选)
  │                              └ 否 ▼
  ├─ 层2 综合服务覆盖且 ROI 划算? ── 是 ▶ 用综合服务(成本门通过)
  │                              └ 否/权威性不足 ▼
  └─ 层3 权威官方源(深度/权威兜底·可接受对接成本) ▶ 用权威源
        └ 都不行 ▶ 降级:缓存→占位(永不代爬·永不拒服务)
```

## 8. 系统要求矩阵（v1.1 核心·每个调研字段为哪个子系统服务）

> 「最大化满足系统要求」的精确含义：probe 的 7 个子系统设计文档对「每个源」各有**真实的字段要求**（下表全部有 3-build 真源出处，非推测）。调研若不产这些字段，源接入后每个子系统都要回头补课——**v1.1 把补课消灭在调研环节**。

| 子系统（设计真源） | 对每个源的真实要求 | 调研必产字段（对应 §3） |
|------------------|------------------|----------------------|
| **编排引擎**（[concurrency-requirements](../3-build/probe-orchestration-concurrency-requirements-v1.0.md) R1.4/R6.1/R4.3/R4.1） | 每节点带「时延档·成本·限流组·可降级·超时预算」元数据；每源 QPS/日配额/并发上限登记进能力注册表（per-source 令牌桶）；hedging 仅免费源开 | 编排适配组：p50/p95 实测时延 · 限流参数 · 超时建议 · hedging 资格 |
| **数据脊柱**（[persistence-and-cache](../3-build/probe-data-persistence-and-cache-design-v1.0.md)） | `persist_policy` 决定能否落库（人物 OSINT/敏感 → ephemeral 禁写 PG·P0 级）；缓存键带 `source_version` 防陈旧污染 | 持久化组：persist_policy 判定 · L1/L2 缓存 TTL · ToS 留存限制 · source_version |
| **隐私合规工程**（[privacy-retention](../3-build/probe-privacy-retention-compliance-engineering-v1.0.md)） | 红线落管线（应用层+PG 触发器双保障） | 同上 persist_policy + PII 标记（调研时即判「此源出不出个人数据」） |
| **gate19+去重图谱**（[gate19-and-dedup](datasource-gate19-and-dedup-v1.0.md) §B9） | 多入口读同一底层数据 → 只接最干净入口，其余标同源；**同源不算交叉验证两票** | 独立性组：源的源 · 同源裁定(主/兜底/rejected) · 验证独立性 |
| **监控雷达+反馈闭环**（[monitoring-radar](../3-build/probe-monitoring-radar-and-feedback-loop-design-v1.0.md)） | `probe_source_reliability` 需冷启动先验；源降级/失效要能被周期巡检发现 | 可靠度组：权威分初值 · 健康检查端点/探测方式 · 断更风险评级 |
| **质量评测**（[quality-eval](../3-build/probe-quality-eval-methodology-v1.0.md)） | golden set + 回归门：源升级/换源后跑回归 | golden 样本 3–5 条（调研时实测的真值留存即回归基线种子） |
| **成本埋点**（[cost-metering](../3-build/probe-cost-metering-design-v1.0.md)） | 每次调用计量入账，需精确计量口径 | 成本组：单价计量口径（按次/按 token/按行）· 免费额度精确数 |

> 反向约束同样成立：**调研不产的字段，子系统就只能用默认值跑**（如限流默认极保守 → 白白慢；persist_policy 默认 normal → 敏感数据误落库风险）。所以 §3 表的 🆕 四组不是锦上添花，是系统正确性的输入。

## 9. 沙箱实测 + 机器可读源卡（v1.1·闸 D 的执行体）

### 9.1 沙箱实测（smoke test·采纳前最后一步）

纸面调研（闸 A/B/C）通过后，**真调一次才算数**（R0.8 实测优先·Q6-C5 诊断结论 ≤24h 精神）：

1. 用免费额度/试用 key 真发 ≥3 个代表性请求（不同品类参数）；
2. 实测记录：真实时延 p50/p95（编排要的不是官网吹的）· 真实限流行为（429 边界）· 响应 schema 与文档是否一致；
3. 取回的真实响应留 3–5 条做 **golden 样本**（喂质量评测回归基线）；
4. 实测失败/与文档不符 → 打回闸 C 重审，**不带病采纳**。

> 涉付费才能测的源：试用额度不可得时标 `cataloged·待R1`，沙箱实测推迟到 R1 授权后、`active` 前补做——**顺序可推迟，步骤不可豁免**。

### 9.2 机器可读源卡（调研最终产物·直灌系统）

每源产出一张 YAML 源卡（替代纯文字报告），**格式对齐 `ledger.yaml` 条目超集**——采纳即灌库，不二次誊抄：

```yaml
- id: <source-id>
  tier: 1-opensource | 2-aggregator | 3-authority     # 三层优先级
  domain: [D15] ;  track: [G-deal]                     # 域+赛道
  capability: { 品类, 覆盖, 时效, 抗污染贡献 }
  access: { api: REST, auth: key, sla: ... }
  cost:   { free_quota: ..., unit_price: ..., metering: 按次 }
  orchestration:                                       # ← 编排直读(R1.4/R6.1)
    latency_ms: { p50: ..., p95: ... }                 #   沙箱实测值
    rate_limit: { qps: , daily: , concurrency: , group: <限流组> }
    timeout_budget_ms: ... ;  degradable: true ;  hedging_eligible: true  # 免费才true
  persistence:                                         # ← 数据脊柱直读
    persist_policy: normal | ephemeral
    cache_ttl: { l1_conclusion: ..., l2_response: ... }
    tos_retention: <ToS留存限制> ;  source_version: v1
  independence:                                        # ← gate19 §B9 直读
    upstream: <底层真实数据源> ;  dedup: primary | fallback | rejected
  reliability_prior: 0.x                               # ← 监控雷达冷启动先验
  golden_samples: <留存路径·3-5条>                      # ← 质量评测回归种子
```
